# 夜之城附属物：模块锚点与生成后 GPU 搜索的评估

日期：2026-11-05。状态：数据审计与实现规格；附属物求解器、GPU 性能测试和网络训练尚未实施。

关联：[放置、跨楼互斥与连接](NightCity_Attachments_And_Links.md)、[建筑生成与分块](NightCity_ProceduralBuildings_Partitioning.md)、[当前立面 Kit](../NightCity_BuildingKit.md)。

后续资产结构细化：[可放置区域网格与源 Mesh 的关系](NightCity_Placement_Surface_Assets.md)。安装区域采用简单辅助表面网格；Profile 保存几何，源 Mesh 的 AssetUserData 保存默认关联，Kit 可以覆盖。

## 1. 结论与选择

**当前程序化楼房建议以“模块携带安装区域模板”为主，生成后统一检查几何与邻楼；没有模板的导入楼体，再走表面提取与候选搜索。GPU 同时可以执行这两种来源的候选检查。**

“都走锚点逻辑”如果指统一接口，可以；如果指所有墙件共享相同几个固定点，不可以。模块无须长得一样，只需各自产出统一的 `AttachmentSite`。一个角墙可以输出两块安装面，一个窗模块可以输出几块实墙带，一个不可安装模块可以输出空集合。

应区分三个问题：

1. **宿主哪里允许安装**：模块模板、生成语义或表面识别负责。
2. **某种附属物在这里采用什么姿态**：规则采样或网络预测负责。
3. **一批候选能否共存**：几何验证与跨楼裁决负责。

空调资产应携带自己的安装基准、支架脚印、实体与净空；建筑模块应携带允许安装区域及禁区。两者配对后才产生实例锚点。只让空调带一个 Socket，或只让墙带一个点，都不完整。

## 2. 实际数据是否支持模块模板

### 2.1 数据范围

本次编辑器保持关闭，复用 2026-11-04 的 MCP 实测快照，并重新统计本地已有的资产目录及外部 Actor 包导出 CSV。两种范围分别记录，没有把“已加载编辑器场景”当成“全城资产”。

统计脚本：[nc_attachment_audit.py](../Scripts/NightCity/nc_attachment_audit.py)。完整结果：[attachment-audit-2026-11-05.json](NightCity/attachment-audit-2026-11-05.json)。

CSV 使用现有 `nc_catalog.py`、`nc_instances.py`、`nc_chunks.py`、`nc_sizes.py` 的导出数据。它们含按二进制布局识别实例的步骤，属于离线解析证据，未在本次通过引擎逐实例复核。计数按源网格短 ID 汇总；MCP 快照中两个短 ID 在不同资产路径下有副本，完整路径数另记。

“建筑外部件”沿用 `nc_city.py` 的路径与关键词筛选，去掉显式室内及一批基础设施词；“墙/窗/门”是该集合中的命名子集。名称不能证明面平整、墙体可承载或位置可以安装。`cct_cpz_building_a_f_6m` 这种不透明命名仍落在 `other`，所以不能用子集占比反推全城所有立面的比例。

### 2.2 重复量高，但种类并不只有几种

| 本次重新统计的范围 | 结果 | 对方案的意义 |
| --- | --- | --- |
| MCP 中 `wbr_cha_building_b_wall_w600_h400_ac` | 同资产 6,229 次；局部 AABB 600 × 50.2 × 400 cm | 高频模块标一次模板，可复用数千次 |
| 离线外部建筑件命名集合 | 5,751 种网格，2,515,152 次摆放 | 不能逐实例人工标点 |
| 其中按命名识别的墙/窗/门 | 2,025 种，937,175 次摆放 | 需要模板家族与例外，不能只有一种墙模板 |
| 墙/窗/门的频率覆盖 | 前 50 种覆盖 33.714%；前 100 种 48.586%；覆盖 80% 需 335 种，90% 需 532 种 | 几十个资产的人工配置不足以覆盖这个子集；这里是使用次数覆盖率，不是放置成功率 |
| 命名中的转角类别 | 935 种，260,513 次摆放 | 转角、内凹和不同夹角须有自己的区域生产者 |
| 外部建筑件中可由命名识别的已使用 Kit | 38 个，覆盖 1,556,499 次摆放 | 有家族复用依据；这是已使用且筛选后的集合，不是资产目录中的全部 Kit |

墙/窗/门集合里，按“水平短边 ≤ 100 cm、水平长边 ≥ 200 cm、高 ≥ 150 cm”筛出的薄盒候选覆盖 78.954% 的摆放。**这个数字只适合排定模板审查顺序，不能宣称 79% 的件已经有可安装平面。** AABB 不能区分实墙、玻璃、栅格或镂空。

### 2.3 尺寸相似不代表锚点相同

MCP 中以下两个资产落在同一个近似 6 × 0.5 × 4 m 尺寸组：

- `SM_C351A38A42B01B7D`：`...building_b_wall_w600_h400_ac`，600 × 50.2 × 400 cm。
- `SM_5674B1687D5C13A5`：`...building_a_wall_window_w600_h400_ag`，600.29 × 50.14 × 399.99 cm。

名称已明确区分墙件与带窗件。它们可以共享外层参数格式，但窗洞、支架位置必须各自确认。此处没有做这两个网格的逐三角形开洞测量，也没有把名字里的 `_ac` 当成“带空调”：它是变体后缀，不能据此生成空调语义。

还有 350.2 × 350.3 × 400 cm 的凸角墙，以及 3/6/12 m 宽、2/4/8 m 高等不同模数。直接把所有资产归一化成一个矩形再贴同样的几个点，会丢失这些差别。

### 2.4 缩放必须进入规则

焦点墙 6,229 个实例中，5,139 个缩放为 `(1,1,1)`，414 个为 `(2,1,1)`，还存在其他非均匀缩放。离线外部建筑件集合中约 39.47% 不是单位轴长，约 32.25% 为非均匀轴长。统计容差为 0.001，CSV 的轴长来自矩阵行长度，不能据此统计镜像或负缩放。

因此安装区域可以跟墙拉伸，**空调机身不应自动跟着墙拉成两倍宽**。模板必须区分“随模块缩放的位置”“固定物理尺寸的设备”“距窗边固定距离的约束”。

## 3. 方案 A：模块携带安装区域和少量明确锚点

### 3.1 数据放在哪一层

建议为 `FCSCityFacadeModule` 增加一个可选的 `AttachmentProfile` 引用。模板是共享的数据资产，引用源 Mesh 与配置版本，不必给每个实例创建 UObject，更不必修改全部导入网格。

| 数据 | 应由谁携带 | 最小内容 |
| --- | --- | --- |
| `ModuleAttachmentProfile` | 建筑模块 / Kit 槽位 | 局部安装框架，区域多边形及孔洞，允许类别，门窗禁区，缩放规则，模板版本 |
| `AttachmentAssetSpec` | 空调、招牌等资产 | 自身安装框架，安装脚印，机身与支架代理，必要净空，允许姿态和尺度，连接端口 |
| `AttachmentSite` | 生成出的模块实例 | 宿主 ID、稳定区域 ID、世界变换、模板引用、街道/店铺/服务侧上下文 |
| `AttachmentRequest` | 建筑功能或作者输入 | 要放什么、服务哪个空间、数量、优先级、候选区域、是否允许缺省 |
| `AttachmentCandidate` | 求解过程 | 需求 ID、区域 ID、资产变体、姿态、占用代理、评分、输入版本 |

UE Socket 可以表达明确的安装框架，但单独的 Socket 不表达可用区域、开窗禁区、资产尺寸和邻楼冲突。可以导入 Socket 作模板的一部分，不能把“有 Socket”当成最终有效位置。

新生成建筑优先使用已知的 Face/Storey/Bay/Slot 语义。给既有 NightCity 场景补附属物时，HISM Actor 往往按 Mesh 聚合，不能把一个 HISM Actor 当成一栋楼；需要额外的宿主描述或离线归属结果。不能仅靠“最近墙件”断定店铺或住宅归属。

### 3.2 模板输出区域，设备在区域内求位置

统一的区域描述可以是：

```text
SiteTemplate {
    TemplateId, SurfaceId, AllowedCategories
    FrameLocal = (Origin, U, V, OutwardNormal)
    AllowedPolygons, HolePolygons
    ForbiddenVolumes[]
    PlacementPolicy, ScalePolicy, Ports[]
}
```

对于平面安装，先把模板变换到真实尺寸，再在平面坐标中求解：

```text
R = 安装区域扣除孔洞和禁区
F(asset, rotation) = 该姿态下的支架安装脚印
ValidCenters = R ⊖ F(asset, rotation)      # 多边形腐蚀 / Minkowski 差
Candidates = Sample(ValidCenters, request.rule, stable_seed)
```

这样候选中心落在区域内还不够，整个脚印也必须在允许区域内。窗洞不能靠只检查四角或中心漏过去。设备机身向外突出的部分另做三维碰撞，不要求机身投影全部贴着实墙；这由具体安装规则决定。

适合的模板生产者包括：实墙面、窗侧实墙带、窗下设备带、店面招牌带、转角的各独立侧面、屋顶设备区、平台边缘。跨两个模块的长招牌可以对同宿主、同用途、共面且连续的区域做并集后求解，不能因为 Mesh 分界就强行切断；也不能跨不同店铺自动合并。

### 3.3 一个可直接实现的壁挂空调流程

以下参数属于项目资产配置，不预设现实安装规范：

```text
输入：request、候选宿主区域、若干空调装配规格、固定场景代理
1. 按 request 过滤服务空间、允许类别、楼层和立面用途。
2. 选空调 + 支架装配规格，再计算其脚印；不能先用统一球间距挑点。
3. 将脚印放进 ValidCenters，得到有限的局部位置与朝向。
4. 对齐空调的 MountFrame 与墙面框架，保持设备自身尺寸。
5. 检查机身/支架、进排风配置净空、维护侧和开窗/通道保留体积。
6. 合法候选参与邻楼统一裁决；未选中保留需求和原因。
7. 通过后同时提交机身、支架、短接管及空间占用。
```

需求不能简单等于“每个墙模块放一台”。一个 6 m 模块未必是一个房间；数量来自作者设定的楼层服务单元、户型或设备密度。招牌需求相应绑定店铺或楼体标识，先确定用途，再选择招牌带与朝向。

设宿主变换为 `p_world = A p_local + t`，位置按该变换更新；表面法线按 `normalize(A^-T n)` 更新，再与变换后的切向重建正交安装框架。设备使用该刚性框架和自身允许尺度，不能盲目继承宿主全部缩放。镜像、超出模板尺度区间或拓扑改变时，重新验证模板或走回退；窗边固定距离应在实际尺寸上重新求值。

### 3.4 与当前代码的衔接

当前 [`CSCityFacadeKit.h`](../Source/CSRoadNet/Public/CSCityFacadeKit.h) 已有墙、窗、门、转角、女儿墙、屋顶六类槽位，以及 `QuarterTurns`。[`CSCityFacade.usf`](../Shaders/Private/CSRoad/CSCityFacade.usf) 已计算每件的 Side、Storey、Bay、Slot 和实际变换，适合在选定槽位后同步产出区域实例，或者由后续 Pass 用相同输入重建。

注意 shader 中 `FacadeEmit(... Anchor ...)` 的现有 `Anchor` 是**包围盒对齐用的比例位置**，并非空调安装锚点。当前 `FCSCityFacadeModule` 只有 Mesh 和 QuarterTurns，没有本文的安装模板、窗洞区域或设备需求。

这里也修正时间差：较早的建筑分析记录过一层一个模块的 `AssembleBlock`；当前工作区已经有 GPU 立面拼装代码，本次以当前源码为集成依据，没有重新编译验证它。

生成时应保留独立的区域身份，不能使用 `InterlockedAdd` 写出的实例缓冲槽号。推荐由宿主的持久 ID、逻辑立面/楼层/开间身份与模板区域 ID 组合。当前局部线程编号和 32 位 seed 可用来随机选择，不能直接充当长期关系的唯一 ID；改变开间数时还须明确身份迁移规则。

**方案 A 的代价**主要是模板制作与语义维护。通过“规则提取初稿 → 按家族复用 → 人工核对例外 → 缓存到资产”可以摊薄；不能把相同尺寸的所有件自动视作同一模板。

## 4. 方案 B：楼体生成后提取表面，再用 GPU 搜索

### 4.1 可执行流程

```text
固定版本的楼体几何 + 语义属性 + 邻域代理
  → 提取连接且近似共面的 SurfacePatch，保留边界、孔洞与来源
  → 外部/内部及用途判别，扣除门窗、通道与不可安装区域
  → 按设备脚印缩小可行区域
  → 有限的位置 × 资产 × 允许姿态候选
  → GPU 分批做支撑、实体/净空与可见性查询
  → 每个需求保留若干备选，建立跨楼冲突
  → 一致裁决后输出正式实例
```

对曲面不应把整面硬塞成一个平面。可分小片、检查局部法线变化和支架适配，或使用专用支架类型。共面但不相连的碎片不能只按平面方程合并；必须保留真实覆盖范围，避免把缝隙、洞口填成实墙。

**“临时摆物体”应是候选变换与碰撞代理放进 GPU 缓冲，并非真的创建上万个 Actor 或逐个更新可见实例后查询。** 候选同时进入场景碰撞会互相阻挡，渲染可见性和碰撞刷新时序也会影响结果。固定楼体输入与待决候选分开保存，最终通过的候选再实例化。

### 4.2 穷举解决不了缺失的语义

找到平面只能证明“有这个几何面”，不能证明“这面允许装空调”。玻璃、装饰板、纹理画出的窗、封闭内部墙、需要开合的窗扇以及店铺归属，需要生成属性、模板、材质语义、人工标签或网络补充。

对自有生成器而言，先丢掉楼层、开间、窗门信息，再从三角形猜回来，是额外开销。对来源不明的合并模型而言，这个逆向步骤才更有价值。提取结果也可以缓存成 `AttachmentSite` 或模板，下次不必再逐实例从零提取。

### 4.3 候选量和组合量是两件事

单个面的离散搜索可写成：

```text
Npose ≈ ceil(W / stepU) × ceil(H / stepV) × Nasset × Nrotation × Noffset
```

例如假设 6 × 4 m 的墙、25 cm 网格、8 个装配变体、4 个允许朝向、1 档离墙偏移，得到 `24 × 16 × 8 × 4 = 12,288` 个原始候选。若粗筛每个候选用 64 个查询点，就是 786,432 次查询；10,000 个这样的面约 78.6 亿次。**这些是示例参数下的运算量，不是耗时实测，64 点也不构成完整碰撞证明。**

如果规则先给出 16 个有意义的位置，再试相同 8 个变体和 4 个朝向，就是 512 个候选，数量少 24 倍。不能把这一比例直接当成速度倍数：表面提取、索引、GPU 占用、排序和裁决仍有成本。

位置、姿态本来是连续量，任何“GPU 穷举”都只能穷举选定离散集合。分辨率过粗会漏掉可行摆法；应采用语义先筛、粗到细、预算可调的搜索，预留按需扩充候选的路径。

而多个附属物选哪组是组合问题。即便单个候选检查全部并行，如果有 M 个需求、每个 K 个备选，同时穷举布局仍有数量级 `K^M` 的组合。GPU 并行碰撞查询不能自动解决跨楼一致性。

### 4.4 当前可复用的 GPU 基础及限制

[`CSVineTriangleSurface.cpp`](../Source/ComputeShaderGenerator/Private/CSVineTriangleSurface.cpp) 已有区域内场景三角形准备、Nanite/普通网格路径和内存预算；[`CSGpuTriangleUtilities.ush`](../Shaders/Private/CSGpuTriangleUtilities.ush) 有 LBVH 工具；[`VineTriangleProjection.ush`](../Shaders/Private/VineTriangleProjection.ush) 有最近三角形查询。

这些可以作为几何查询底层，**现有最近点查询不是安装区域提取器，也不是 OBB/装配体碰撞验证器**。还要增加完整查询、来源 ID、区域语义及错误处理。现有提取流程允许部分 Nanite 结果的情形，若用于硬碰撞判定，必须额外验证覆盖完整性；缺失几何不能当作空白区域通过。

优先使用区域内的固定几何快照或保守代理。全局距离场可以辅助粗筛，但不能作为唯一最终裁决：官方文档说明它是随相机的低分辨率 clipmap，薄表面及非均匀缩放还有精度限制。以此直接决定永久布局，可能使结果随视点或表示精度变化。[Epic：Mesh Distance Fields](https://dev.epicgames.com/documentation/en-us/unreal-engine/mesh-distance-fields-in-unreal-engine)

初版可使用保守的多盒体/凸体代理，允许一定误拒；精细化时再用三角形 BVH 和相应体积测试。只采样中心、表面若干点或只测三角形相交，都可能漏掉薄障碍或完全包容关系。SDF 若用于硬接受，需要明确覆盖、误差上界及安全余量，不能把插值值直接当成精确距离。

现有实例生成可能只在 GPU 上掌握最终变换，因此查询底层能否采集这些自定义实例源也须验证；对自有生成器，直接让建筑描述与 GPU 变换生成查询代理更可靠，不依赖渲染场景“恰好已刷新”。

## 5. 两条路线共用的约束与跨楼求解

把每个装配候选记为 i，二元变量 `x_i` 表示接受与否，`valid_i` 来自固定场景硬验证：

```text
x_i ∈ {0,1}
x_i ≤ valid_i
对同一需求 r：sum(x_i, i ∈ candidates(r)) ≤ 1
对每对硬冲突 (i,j)：x_i + x_j ≤ 1
目标：在优先级约束下提高总评分，或使用稳定顺序的贪心近似
```

必需需求用“放置或明确未满足”的状态表达；两个手工锁定方案冲突时报告矛盾，不能悄悄选择一方。软评分包含用途契合、街道可见性、立面节奏及对原位置的保持；硬碰撞不能用软评分抵消。

一个可实现的函数分界如下，名称为建议接口，尚未接入代码：

```text
BuildSites(building, moduleProfiles, fallbackGeometry) -> sites
Propose(request, sites, assetSpecs, budget)            -> candidates
EvaluateFixed(candidates, immutableScene)             -> validity, scores, blockers
BuildConflicts(candidates, spatialIndex, rules)        -> graph
Resolve(graph, requests, stableOrder)                  -> solution
CommitIfCurrent(inputVersion, solution)               -> instances, links, hostEdits
```

同一需求的备选、实际空间冲突和连接依赖都参与受影响集合的构建。GPU 很适合并行 `EvaluateFixed` 及粗筛冲突边；第一版 `Resolve` 可以在 CPU 对受影响连通部分做稳定贪心，得到可调试的基线。若回读成为瓶颈，再把裁决搬到 GPU；不能用原子写入先后当优先级。仅保留 top-K 可能删掉唯一可行备选，拒绝过多时按预算扩充，并暴露截断原因。

尽量让几何查询、候选筛选连续留在 GPU，CPU 只接收紧凑的有效候选及必要冲突数据，避免逐点同步回读。Epic 的 GPU PCG 文档也建议减少 CPU/GPU 传输并连续组织 GPU 节点；本项目已有自定义 RDG/实例输出路径，不要求为此改成 PCG Graph。[Epic：GPU PCG](https://dev.epicgames.com/documentation/en-us/unreal-engine/using-pcg-with-gpu-processing-in-unreal-engine?application_version=5.7)

分块查询使用包围体相交，而非只把中心点放进格子；读取范围覆盖最大装配突出、净空和连接跨度。直接邻域外还可能通过冲突链传播，重算范围须按冲突连通部分确定。暂未加载的邻楼使用持久描述/代理；描述缺失则待解析。结果带输入版本，旧异步结果不可覆盖新楼体。

Tiny Glade 的共享 Contact / 连接解协议继续适用：两端端口形成一个连接需求，桥/管线、支架和宿主开口是一份候选装配，整体参加上述求解并原子提交。一对楼允许多条链接，键包含端口与链接身份。GPU 搜索不能绕开这层关系和生命周期逻辑。细节见[连接方案](NightCity_Attachments_And_Links.md#6-连接物怎样沿用-tiny-glade)。

## 6. 深度学习应放在哪一层

两条路线都能接网络。建议先让网络学习**候选区域和偏好排序**，几何硬验证与跨楼一致性保留显式求解。

### 6.1 可训练的输入输出

模板路线的输入可以是区域多边形/孔洞、模块或 Kit 编码、楼层/店铺/街道特征、邻域占用、设备规格及需求。无模板路线则增加网格采样点/法线、材质语义或表面图。任意模型名都不能替代这些数据定义。

一个起步模型可以是区域编码器 + 候选评分 MLP；需要邻域关系时再加图网络。输出 `score(request, site, asset, pose)` 或每区域的 top-K `(u,v,angle,offset,asset_id)`，同时有拒绝/低置信度状态。姿态残差必须投影回合法安装区域，再通过统一几何验证。

也可以学习表面上的分类热图：空调允许区、贴墙招牌区、挑招支架区、禁止区。对高复用模块，先在模块局部空间预测并缓存，实例上只结合环境重新评分；没有必要对同一墙件的数千个副本重复编码同一几何。

### 6.2 数据与损失

现有 NightCity 摆放是潜在正例，但不能直接当现成标注集。先识别附属物类别、推断安装面与服务对象，用距离、法线、支架接触及人工抽查过滤低置信匹配；当前快照没有直接提供房间/店铺归属。留空的墙也不能一概作负例，因为它可能只是没有设备需求。

训练可采用：

- 区域用途分类损失或人工接受/拒绝标签。
- 同需求候选的排序损失；成对偏好比“唯一正确位置”更合适。
- 接触与姿态残差损失；保留多个合理解，避免回归到两种方案之间的无效平均位置。
- 由可靠几何检查器产生的碰撞负例；语义不适合的负例另行标注。

训练/验证应按 Kit、建筑家族和空间片区隔离，避免同一 Mesh 的重复实例分到两边制造虚假的泛化。报告 top-K 可行召回率、人工接受率、硬冲突率与推理代价；不只报告位置误差。

已有研究证明可用场景/物体点云预测不同 6DoF 姿态的碰撞，但其任务和数据分布并非城市外挂设备，不能把论文速度或准确率直接套过来；本项目有已知网格和强规则时，学习碰撞不应优先于直接几何验证。[Danielczuk 等：Object Rearrangement Using Learned Implicit Collision Functions](https://arxiv.org/abs/2011.10726)

当前尚无整理好的宿主标注、训练集或模型评估结果，所以不能宣称网络能免去模板制作；更实际的第一用途是辅助生成模板初稿及给候选打分。

## 7. 成本、适用范围与实施取舍

| 比较项 | A：模块模板 | B：生成后提取与搜索 |
| --- | --- | --- |
| 自有 Kit 生成的楼 | 很合适，直接保留生成语义 | 可作验证；重新恢复已知语义成本多余 |
| 陌生合并楼体、手工异形面 | 要补模板或专用生产者 | 覆盖更灵活，但仍需语义与表面质量检查 |
| 前期工作 | 模板家族、开洞和缩放规则 | 表面分割、外部面判别、几何查询、搜索预算 |
| 高频重复模块 | 模板与局部几何可大量复用 | 应缓存提取结果，否则重复付费 |
| 变体和拉伸 | 参数化区域后重新适配脚印 | 实际几何天然参与，但须重新提取或更新缓存 |
| 可控性与解释 | 拒绝原因易对应规则/模板 | 需记录提取失败、语义置信度、离散搜索遗漏 |
| 跨楼互斥 | 仍需共同求解层 | 同样需要，单候选 GPU 检查不能替代 |
| 深度学习 | 学区域内分布、评分与模板初稿 | 学表面用途、候选及评分；数据需求更高 |

建议实施顺序：

1. **先限定一个 Kit 家族和三类附属物**：普通墙、带窗墙、转角，加空调、贴墙招牌、挑招。先人工核对小量模板及设备装配规格，不承诺它们代表全城。
2. **让当前立面生成器输出安装区域及禁区**，保留楼层/开间语义和稳定身份。实现前述统一候选/约束协议，先得到可解释的跨楼基线。
3. **GPU 加速候选的几何检查**，继续使用同一模板与需求输入；是否搬动裁决层由实际回读开销决定。
4. **给无模板资产添加提取回退**，提取结果可以转成共享模板；高频资产优先人工校正，低置信度区域保持禁用或待审。
5. **收集接受/拒绝与人工改位数据，再训练评分或区域预测网络**。模型不改变硬约束接口。

原型必须做对照：A、B、推荐混合流程使用同一组楼、同一批需求、相同设备尺度与最终几何验证器；包含普通墙、窗洞、转角、非均匀缩放、狭巷和跨楼连接。分别记录模板制作量、候选数、表面提取/GPU 查询/回读/裁决耗时、峰值显存、未满足需求、错误接受与误拒，以及小范围编辑时的位置变化数量。冷启动与缓存后的增量更新分开统计。

本次只运行了只读数据统计并核对源码，没有运行该原型、GPU 基准、网络训练或引擎编译。现有证据足以支持优先模块区域模板的架构选择，**不足以给出全城模板可覆盖率、放置成功率或毫秒级性能结论**。
