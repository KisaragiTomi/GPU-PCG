# 减少更新、重复写入与每组件固定成本：实现与结果（2026-10-02 ～ 10-03）

[InstanceCullingOptimization.md](../../InstanceCullingOptimization.md) 第三阶段（§6.1、§6.2、§7）与第四阶段里实测是热点的那一项（§6.4）的落地记录。
每一项都留了对照开关，数字都是同一个进程里的交错 A/B（3 对，判据是各对同号）。基线见 [Baseline_20261002.md](Baseline_20261002.md)。

| 项 | 做了什么 | 收益（实测） | 开关 |
| --- | --- | --- | --- |
| CPU 增删合批（§6.1） | `BeginInstanceUpdate` / `EndInstanceUpdate`；`bMarkRenderStateDirty=false` 不再重排；重排换成基数排序 | 10 万个实例：连改 8 个 82.5 → 7.3 ms；单次增删 12.6–13.1 → 7.2–7.9 ms | API，无开关 |
| 剔除派发范围（§6.2） | CPU 源按行数派发，不按容量 | 并在下一行的数字里 | 无（恒开） |

## 1. CPU 实例增删合批（§6.1）

### 接口

```cpp
// 一串任意混合的改动，一次重排、一次上传
{
	FCSGpuInstancedUpdateScope Scope(Component);            // = BeginInstanceUpdate()，析构时 EndInstanceUpdate()
	const int32 Index = Component->AddInstance(Transform);   // 下标、句柄当场有效
	Component->RemoveInstanceByHandle(Handle);
	Component->UpdateInstanceTransform(Other, NewTransform);
}                                                            // 最外层 End：排序 + 打包 + 上传 + 渲染状态，各一次

Component->RemoveInstances({ 2, 5, 9 });                     // 一次删一批，下标是调用那一刻的
```

| 区间内 | 行为 |
| --- | --- |
| 下标、句柄、`GetInstanceCount()`、按句柄的查 / 改 / 删 | 当场生效 |
| 画面、GPU 缓冲、`GetGpuLayout()`、包围盒 | 停在区间之前 |
| `GetPackedInstances()` / `GetClusterBounds()` / `GetPackedInstanceSlots()` | 读的时候当场补一次打包（只是 CPU 那一半） |
| 嵌套 | 只有最外层的 End 落地 |

`UpdateInstanceTransform(..., bMarkRenderStateDirty=false)` 现在真的只记脏：排序、打包、上传都攒到下一次要更新的调用。
此前它仍然当场整份重排，只省上传 —— 基线发现 7。

结果与逐个调用**逐位相同**（packed 行、簇球、行表、句柄、随机数）：发槽次序只取决于两张身份表，不取决于打包发生在什么时候。

### 数字（游戏线程上一次调用，ms，10 万个实例）

| 操作 | 经典路：前 | 后 | Nanite 路：前 | 后 |
| --- | --- | --- | --- | --- |
| `SetInstances` | 14.7 | 9.6 | 12.4 | 7.1 |
| `AddInstance` / `RemoveInstance` / `UpdateInstanceTransform` 各一次 | 12.6–13.1 | 7.2–7.9 | 11.0–11.7 | 5.5–6.2 |
| `UpdateInstanceTransform` × 8，前 7 次 `bMarkRenderStateDirty=false` | **82.5** | **7.3** | 81.7 | 5.6 |
| `AddInstances`（一批 8 个） | 12.9 | 7.3 | 11.1 | 5.5 |
| 区间里 8 个 `AddInstance` | 逐个调约 101 | 7.1 | 逐个调约 90 | 5.5 |
| 区间里 24 个混合改动（加 / 删 / 改各 8） | 逐个调约 310 | 7.4 | 逐个调约 270 | 5.5 |
| `RemoveInstances`（8 个） | 逐个调约 101 | 7.5 | 逐个调约 90 | 5.5 |

单次调用从 13 ms 到 7 ms 是排序换的：原来对下标数组做比较排序、每次比较间接读一次 Morton 码表，
换成对 `(码, 下标)` 做基数排序（稳定，同码的按数组下标）。剩下的 7 ms 是逐实例算包围球、打包矩阵和一次上传。
1 万个实例时各约 1/10。原始表：[data/cpuops_20261002_after.report.md](data/cpuops_20261002_after.report.md)。

### 验证

`GpuInstancedMesh.BatchUpdate`：同一串 8 个操作逐个调用打包 8 次、成批 1 次，结果逐位相同；嵌套；区间内读 packed 行；
`bMarkRenderStateDirty=false` 一串只打包一次；`RemoveInstances` 的重复 / 越界下标；注册在世界里时区间内零次阻塞刷新、
18 个改动成批只有 1 次（与单个 `AddInstance` 相同）。

## 2. 剔除派发范围（§6.2）

`InstanceCullCS` 的派发范围从"容量"改成"布局里的源行数"。CPU 实例数组的容量按 1.5 倍棘轮，多出来那三分之一的线程组一进来就返回，
现在不派了。GPU 源的行数只有 GPU 计数器知道，布局里记的就是容量，仍然整段派发。

**GPU 源没有做间接派发**：基线量过，容量是活跃数 8 倍（多扫 70 万行空槽）才多 0.06–0.08 ms，而间接派发要多一个建参数的 pass。
下面 §4 的数字说明每多一个 pass 在组件多的时候是有固定成本的，这笔账不划算。

## 3. Nanite 路跳过无变化的写入（§7）

### 协议

老契约：GPU 实例源的生产者原地重写 buffer、从不通知，所以 Nanite 替身**每帧**把整份源重抄进 GPU-Scene，
VSM 跟着每帧把这批实例的缓存页作废。新增一份逐源自愿的承诺：

```cpp
FCSGpuInstanceSourceGPU Source;
Source.bNotifiesChanges = true;                 // 承诺：每次原地改写行 / 计数器 / custom data 之后都通知
Component->SetInstanceSourceGPU(Source);        // 交接本身算一次改动

// 之后每次原地重写 buffer：
Component->NotifyInstanceSourceChanged();       // 不阻塞；Nanite 路在下一次渲染之前重写
```

| 情形 | 承诺了通知的源什么时候重写 GPU-Scene |
| --- | --- |
| 数据没变、相机没动 | 不写 |
| `NotifyInstanceSourceChanged()` / 重新交接 | 当帧 |
| 图元动了、代理重建 | 当帧（与 CPU 源同一条路径） |
| 开着距离带，视点挪了 10 cm 以上 | 当帧（带要跟相机走） |
| `r.CSGpuInstanced.Nanite.SkipUnchangedWrites 0` | 每帧（对照 / 排查漏通知） |

没承诺的源（默认）行为一个字没变。经典路不看这面旗子 —— 剔除本来每帧现读 buffer。点云源也有同一面旗子，
点刷不承诺（它在渲染线程的帧内回调里追加点）。

**承诺了却漏通知**，Nanite 路的画面停在上一次写入的样子，没有任何报错。所以开之前要把那一族所有写这批 buffer 的地方数一遍；
怀疑漏了就把上面那个 CVar 设成 0，画面对了就是漏了。

### 谁接入了

经 `CSShaperSteps::HandOverInstanceSources` 交接的生产者统一在那里开（`FHandoverOptions::bNotifiesChanges`）：
交出去的源带上旗子，判定"不用重新交接"的源在那里补一次通知 —— 生产者重散 / 重打包之后都会走到这个函数。

| 生产者 | 状态 | 依据 |
| --- | --- | --- |
| 地被（`ACSGroundActor` 的 `CoverBuffers`） | 已接入 | 只有 `CSGroundCover::Scatter` 一处写，写完必到交接；容量变了换新 buffer、走重新交接 |
| 建筑周边灌木（`BushBuffers`） | 已接入 | 同上 |
| 石阶 / 石子、裙边摆件 | 没接 | 数量小，没有逐条核过写入路径 |
| 房子的门框砖、柱、瓦、藤、摆件（`ACSHouseActor`） | 没接 | 另一个会话正在改 `CSHouse*`，没有碰；实例数也小（几十到几百） |

## 4. 每组件的固定成本（§6.4 的第一刀）

基线发现 2：同样 10 万个实例拆成 256 个组件，整帧 6.2 → 11.4 ms，瓶颈是渲染线程。每个代理每帧各自登记全部常驻流、
各派 5 个 pass。这一步没有做真正的跨组件合批（见 §5），只把每个代理的固定开销压下来：

| 改动 | 内容 |
| --- | --- |
| 只登记剔除用到的常驻流 | `FCSMeshRenderThreadEdit` 多了一个流位图参数。剔除只碰间接参数与本叶子的 aux 流（5–6 条），基础网格的位置 / 切线 / UV / 颜色 / 索引不再每帧登记 |
| CPU 源的实例数走 uniform | 以前每个代理每帧建一块 4 字节的计数 buffer 再清一遍；现在是 `InstanceCullCS` 的一个 permutation。CPU 源每代理每帧 5 个 pass → 4 个 |
| 只剔本场景的代理 | 登记表是全进程一张（编辑器世界、PIE、材质 / 缩略图预览场景都在里面），以前每个视图族把所有场景的代理都剔一遍 |

`r.CSGpuInstanced.LeanCullSetup` 是位标志（默认 3）：位 0 = 只登记用到的流，位 1 = 实例数走 uniform，0 = 旧做法。
"只剔本场景的代理"没有开关（纯粹是不做白工）。

### 为什么逐 LOD 计数器的清零 pass 留着

试过把它并进 `BuildArgs`（抄完间接参数顺手清零），做了单项与两两组合的消融。单独开是正收益，但与"实例数走 uniform"同开 ——
每个代理的剔除前面一个清零 pass 都不剩 —— GPU 反而慢了：

| 组合（256 个组件，`top` 机位，对旧做法） | Frame | GPU |
| --- | --- | --- |
| 只登记用到的流 | −0.30 | 0 |
| 实例数走 uniform | −0.56 | −0.22 |
| `BuildArgs` 清计数器 | −0.30 | −0.20 |
| 流 + uniform（**现在的默认**） | **−0.73** | −0.23 |
| 流 + 清计数器 | −0.56 | −0.20 |
| uniform + 清计数器 | −0.30 | **+0.13** |
| 三项全开 | −0.46 | **+0.13** |

各格都是 3 对同号。可见数逐项相同，不是画错；机制没有查清。结论是这条路上"少一个 pass"与"更快"不是一回事，
省 pass 的改动要带开关做组合消融。那一项已经从代码里撤掉。消融的原始表（当时的开关还有第三位 4）：
[单项](data/ab_lean_bits_single_20261002.ab.md)、[两两组合](data/ab_lean_bits_pairs_20261002.ab.md)。

### 验证

`VisibleSourceIndex.Picture` 里加了一段：建图方式 0 / 3 / 1 / 2 来回切，画面逐像素相同、逐 LOD 可见数不变。
全套 `PCGPlugins` 244 条在默认配置与 `-CVars "r.CSGpuInstanced.VisibleSourceIndex=0,r.CSGpuInstanced.LeanCullSetup=0"` 下各跑一遍，
红的只有四条既存红。

## 5. 没做的，以及为什么

| 方案里的项 | 状态 | 理由（实测） |
| --- | --- | --- |
| §6.2 GPU 计数驱动的间接派发 | 不做 | 多扫 70 万行空槽才 0.06–0.08 ms，换一个 pass 不划算 |
| §6.3 GPU 源分簇 / 可见簇工作列表 | 不做 | 剔除 pass 现在 100 万个实例全可见 0.48 ms、CPU 源全不可见 0.015 ms、GPU 源（无簇表）全不可见 0.125 ms，没有可省的量级 |
| §6.4 聚合原子计数 | 不做 | 同上：整个 InstanceCull 才零点几毫秒 |
| §6.4 真正的跨组件合批（一个 dispatch 剔所有组件） | 没做 | 要把各组件的源行、可见缓冲、间接参数并进共享缓冲，是常驻流所有权的重构。256 个组件现在是 10.4 ms 对引擎 ISM 的 5.4 ms，差距还在；组件数到这个量级的内容出现之前不值得动 |
| §5.3 紧凑 LOD 区段 | 不做 | 见 [VisibleSourceIndex_20261002.md](VisibleSourceIndex_20261002.md)「没做的」 |
| §8 HZB 遮挡、多视图 | 没做 | 方案自己排在最后，"有明确收益后再实施"；现有内容是开阔地被，没有量到遮挡密集的场景 |
| 经典路的阴影（方案里没有） | **待定** | 基线发现 1：开投影时的大头（100 万个实例 `edge` 机位 20.5 ms）。要另外立项：让经典路进 VSM、或给回退级联单独剔除、或把投影交给 Nanite 路 |
